## Scope and conclusion

The most defensible conclusion is that Paperclip is a serious reference for execution correctness and a useful source of concrete scaling lessons. It is not evidence that a TypeScript control plane cannot support thousands of active agents. Its Rust runner, durable command identities, uncertain-outcome handling, cleanup fences, transactional notifications, private liveness pool, and bounded presentation delivery are strengths to retain. The identified limitations concern particular contention boundaries, historical read work, queue policy, deployment topology, and configuration lifecycle. Each requires its own remedy; “rewrite in Rust,” “add Kafka,” or “split into microservices” would not establish those remedies.

For Agent Teams, preserve the intended separation: **Agent Runtime v3 S1–S5 delivers the ordinary execution runtime; C0–C3 is the separately owned capacity/fleet delivery**. Assume the approved plans are implemented correctly when comparing target designs. Do not score unfinished code against a completed competitor, or reinterpret S1–S5 completion as qualification of thousands of simultaneous active agents. The existing capacity plan already addresses many lessons below. The useful output is a sharper acceptance contract and a few explicit product choices, not duplicate architecture.

This report inspects source and committed test/evidence artifacts at Paperclip [`61e8d5c7eb097664958e00c30ccd88bb51359043`](https://github.com/paperclipai/paperclip/tree/61e8d5c7eb097664958e00c30ccd88bb51359043). Tests were **not rerun** for this report. “Test covers” means the inspected test asserts that behavior; published benchmark outcomes are attributed to the repository's evidence rather than represented as independent reproduction. A missing fleet qualification is an unresolved capacity claim, not proof of failure.

Agent Teams reference snapshots are Agent Runtime `4bdc93a43b58469f60ca10c0dca512824650c8ac`, Orchestrator `981dd836ca3d35b764561bdc11dc2e0544d83416`, and Platform `7f6eb3746c07dc01751c29a8dbc62e50b5f7ad6d`. Their plans and decisions retain their original accepted/proposed status. [A1–A4]

The cost observations below are targeted hypotheses chosen for transferable lessons, not an exhaustive capacity diagnosis. **This research does not revoke existing scoped qualification or introduce a new gate by itself; only the owning accepted change can alter future acceptance.** The proposed experiments apply to the named future capacity, producer or managed-deployment scope after the owner reconciles them with existing coverage. Existing requirements and proposed deltas are distinguished in the follow-through table. No new defect in Agent Teams is established by this competitor audit.

## Eight findings that change design or acceptance

### 1. The company accounting lock is a real serialization boundary, but neither a proven agent ceiling nor an exact external spending cap

**Implemented fact.** `withAccountingTransaction` takes `FOR NO KEY UPDATE` on the company row before invoking its callback. Usage ingestion then locks the run, validates and persists the receipt, updates usage, and can evaluate budgets. Final settlement and reservation paths use the same wrapper. This couples otherwise independent same-company operations. Different companies can proceed independently. Ordinary reports use a read-only repeatable-read snapshot. [P1–P3]

The key anti-pattern for the Agent Teams target is placing unrelated frequent writes behind a tenant-wide mutable aggregate. Deleting the explicit lock is insufficient: the current monthly-spend projection updates shared company/agent rows on ledger insertion, which creates another shared write dependency. The invariant and every writer must be redesigned together. [P2–P3]

**Counterevidence and limits.** Paperclip's November 3 investigation documents a first eligibility-read optimization that preserves authoritative admission and reconciliation. Its report says the real-PostgreSQL test deliberately holds the company lock: preliminary healthy checks complete while authoritative admission reaches a lock timeout. This is useful contention evidence. The same report explicitly cautions that its lock-acquisition spans include network/database/Node scheduling, do not identify blockers or company distribution, and establish no numerical fleet ceiling. Its sample is predominantly zero-policy exposure checks, so it does not prove that large policy aggregate queries caused the sampled tail latency. [P3]

The append-only accounting design is **proposed**, not the current implemented path. It intentionally changes budget semantics: receipt durability remains strict, while spend projections, threshold detection and cancellation may lag. It calls for partitioned publication, freshness gates, idempotent receipts, and no per-receipt shared counter. The document itself says that this does not prove support for 10,000 active agents. [P4]

**Application to Agent Teams.** Preserve the accepted ADR-0045 baseline: Usage Metering owns immutable observations, Usage Accounting owns attribution/rating and projections, and Consumption Governance owns both soft limits and hard quotas, including reserve/authorize/capture-or-release with identity, revision, expiry and fencing. The proposed tactical dossier does not make that strategic baseline optional. OD-024 owns the remaining basis, estimate/overshoot, period, aggregate and reconciliation details; this research requests no new user vote on whether both modes exist. Keep durable usage evidence separate from enforcement and never describe an estimated admission allowance as an exact provider dollar cap. AR reports technical usage and enforces its accepted execution/capability limits; Platform owns commercial entitlement decisions. An eventual spend view must not replace hard-quota, security or revocation authority. [A2–A4]

**Proposed evidence for the relevant owner scope.** Compare one large tenant with many active runs against the same active population spread across tenants. Measure receipt/settlement rates, query and WAL work, DB lock wait attribution, projection lag, unknown usage, and dispatch latency. Include zero-policy and configured-policy cases. For a hard-reservation policy, race admission against settlement, quota reduction, expiry, and a lost commit response. For soft budgets, freeze the maximum admitted decision age and the fail-closed behavior when the reducer falls behind.

### 2. Per-agent concurrency and infrastructure quotas do not compose a fair fleet admission contract

**Implemented fact.** `startNextQueuedRunForAgent` computes slots from the agent's configured concurrent-run cap. It then reads **all queued rows for that agent** without a SQL limit, derives dependency readiness and issue priorities, sorts them in application memory, and only then stops claiming after filling the available slots. That work grows with the agent's current queued backlog even when there is one free slot; it is not a scan of completed historical runs. The inspected ordering prefers dependency-ready/in-progress work, then issue priority, then creation time. This is a concrete queue shape, not a generalized accusation of unbounded memory everywhere. [P5]

Paperclip also has an execution-admission module with durable project charges, canonical project lock order, replay/conflict detection and exactly-once settlement. Its own module guide explicitly says only internal policy commands/deletion guards are exposed today and claims remain in the heartbeat/native dispatch owners. The adapter explicitly states `recordAdmission` neither checks capacity nor claims work; a composed command must do both under the same locks. Calling it a “broken public concurrency feature” would be false. [P6]

**Counterevidence.** Per-agent limits are real; the policy tests cover consistent dispatch/execution limits. Kubernetes tenant provisioning creates ResourceQuota for pods, requested/limited CPU and memory. There are real resource protections. They answer different questions from cross-tenant fairness, bounded pending bytes, provider-pool saturation, and safe reclaim. [P5–P7]

**Decision for Agent Teams.** Retain C0–C3's owner-local PostgreSQL capacity queue and explicitly bounded claim batches as the first fleet implementation. A broker transports durable messages; the capacity owner must still decide admission, fairness, resource fit and reclaim. C0–C3 already requires pending-count/byte bounds, active resource vectors, tenant/global/provider scopes, immutable classification, persisted fairness state and control-plane reserve. Its Stage K model demonstrates eight grants from 32 competing claims, equal-tenant modeled progress, a bounded-priority/FIFO escape, and fenced reclaim. It did **not** launch real workers. Do not claim it already proves an active fleet. [A1]

For dependency-rich queues, a naive `LIMIT 100` is not a complete fix: an ineligible prefix could hide eligible work. Use indexed eligibility summaries or bounded continuation scans with an explicit reschedule cursor, and test that old eligible work progresses under constant higher-priority arrivals. Avoid copying product dependency policy into AR: Orchestrator determines eligibility/business class; AR consumes the authorized technical class and resource demand.

**Proposed evidence for the relevant owner scope.** Saturate one tenant while another continues. Include large and small resource vectors, long-lived holders, dependency-blocked prefixes, cancel/grant races, queue-full replay, provider-pool exhaustion and allocator restart. State the finite eligible-grant-opportunity bound and its assumptions; no wall-clock guarantee is possible while required capacity remains indefinitely occupied. Throughput without this progress property is not tenant fairness.

### 3. Native event acknowledgement performs historical aggregate work; bounded response size is not bounded database work

**Implemented fact.** `PaperclipControlPlanePort.appendEvent` calls `appendHeartbeatRunEvent` transactionally for validated native events. The event path locks the run row, checks source identities and payload hashes, allocates an event sequence, inserts the receipt, and returns a contiguous source cursor. `contiguousCursor` computes `count(*)` and `max(source_seq)` over the run/source history; gaps add first/missing-successor queries. This happens for the append path and database-level replay path. [P8]

**Inference, narrowly stated.** For a long chatty run, repeated counting can make database work grow with retained source history. Indexes make lookup and ordering useful but do not turn counting every qualifying row into a constant-work operation. The report does not assign a precise asymptotic wall-clock cost or call this the observed system's dominant bottleneck. It identifies a source-backed benchmark candidate. The contention boundary is per run, which is materially better than per company.

**Counterevidence.** There are source-event/source-sequence unique indexes and explicit payload-conflict rejection. A real-PostgreSQL test seeds 5,000 historical events, inserts a gap and late fill, verifies contiguous cursors and replay, and asserts fewer than 16 returned rows and less than 2,048 response-value bytes. It protects correctness and response size. It does not assert `EXPLAIN` buffers, total scanned tuples, or append throughput over increasing history. A different coordinator-store path enforces strict contiguity and uses a latest-sequence lookup; do not claim every Paperclip ingestion path does a historical count. [P9]

**Application to Agent Teams.** Preserve the existing owner append and replay contract. For an ordered producer, a strict contiguous writer can advance its cursor incrementally and project views asynchronously; those mechanisms are compatible. Use bounded batching only within that same ordering/ACK meaning. Add gap tracking only if an identified producer contract actually permits out-of-order acceptance. Source occurrence identity, canonical runtime cursor, reader cursor and reconstructed history remain distinct under the existing plans. If current planned mechanisms already meet the selected source contract, the useful delta is historical-growth measurement, not another store, port or event framework. A maximum source sequence alone is invalid for a path that legitimately permits gaps. [A5]

**Proposed evidence for the relevant owner scope.** Same event rate at short, medium and long histories; multiple independent runs; exact/conflicting replay; DB disconnect after commit; restart while receipt ACK is unknown. Measure query plans/buffers and work per committed event as well as client response bytes. Batching must preserve terminal control and durable ACK meaning. Only for a producer that requires gaps, also fill the first hole before a very long received suffix: advance the contiguous prefix with bounded work per transaction, retain a durable continuation through crash, and distinguish an individually durable receipt from the prefix the producer may delete. Bound gap count, bytes, age and retention according to that source contract. An unsupported gap remains an explicit rejection or incomplete-source outcome, not permission to invent replay.

### 4. Deployment-overlap correctness is valuable, but it is not the topology for indefinite horizontal operation

**Implemented fact.** `deployment-notifications.ts` says “Temporary overlap, not steady-state horizontal scaling.” Its listener is wanted during startup, a default 120-second handoff, or while that process owns native execution. It uses PostgreSQL notifications as hints; durable queues and claims remain execution authority. Browser connections alone do not retain the listener. Company live invalidations are coalesced and carry identity rather than event content or authorization. [P10]

**Counterevidence.** This is not a single-process-only design. The inspected tests deliver committed hints across independent pools, reject outer-transaction rollback/savepoint publication, reconstruct on listener reconnection, scope company refresh, and disconnect/reopen according to the declared lifecycle. Those are precisely the guarantees worth preserving. [P11]

**Decision for Agent Teams.** Declare deployment profiles and long-lived responsibility ownership explicitly. Local and self-hosted profiles need not add a separate distributed allocator service beyond their accepted role map. Preserve required process boundaries and materialize selected roles with their owning features; this is not permission to substitute an in-process topology. Managed SaaS needs a defined worker/pool ownership and dispatch path that remains correct after arbitrary overlap duration, process replacement, and worker movement. Avoid making a deployment grace timer the implicit coordination contract.

The existing Orchestrator JetStream selection remains the integration transport. AR's durable capacity store remains runtime truth. Work notification loss must lead to bounded durable reconstruction, not a fabricated grant, while quiet local installations should use real deadlines and unresolved-work retries instead of empty scans. Sleep/wake obligations and always-on SaaS obligations can have different adapters under the same semantics. [A1–A3]

**Proposed evidence for the relevant owner scope.** Two and then several controllers active beyond any rollout window; process loss between commit and signal; lost/repeated notifications; worker reassignment; isolated control plane; a sleeper awakened for its actual due obligation. State who owns cross-replica browser invalidation and who owns workload scheduling. Neither should accidentally depend on a particular API pod owning a process.

### 5. Protecting cancellation and cleanup under overload is a correctness requirement, not an optional performance improvement

**Implemented strength.** The runner reserves durable outbox bytes for P0 events; ordinary events are rejected at the soft limit. Exhausting the entire reserve produces an explicit unrecoverable/operator-recovery state instead of pretending that safety control was recorded. The inspected test fills ordinary capacity and still appends a P0 diagnostic, and rejects an oversized frame. [P12]

The DB client creates a separate lazy two-connection liveness pool because ordinary queries can otherwise queue ahead of renewal. Renewal checks expiry **after obtaining the row lock**, binds controller identity/attempt, uses a real SQL statement timeout, and does not treat uncertain success as confirmed authority. There is also a separate checkpoint pool. A real-PostgreSQL test occupies both liveness connections, delays two renewals, and verifies preserved ownership after successful renewal. [P13]

The native journal writes command identity before effect; recovered pending commands become `indeterminate` and are not blindly re-executed. The journal refuses additional work rather than compacting away a still-authoritative cleanup receipt. Process-group termination is explicitly insufficient to prove escaped/reparented descendants are gone; higher-level lifetime fencing has a test that prevents reuse while a provider lifetime fence remains held. [P14]

**Remaining scope.** Reserved bytes and two SQL connections do not themselves prove end-to-end stop latency under thousands of active workers. CPU, disk, network, SQL row locks, authenticated control ingress and physical termination can each starve independently. This is not evidence those guarantees are absent; it names the integration experiment needed for the fleet target.

**Decision for Agent Teams.** Adopt the full invariant already reflected in C2: losing a lease closes effect/output authority, but capacity stays charged until fencing/containment is established or an enforcement-backed quarantine explicitly permits reuse. A terminal result, completed task, accepted cancellation, process-group exit, workspace save and cleanup receipt are different facts. Orchestrator owns product continuation; AR/native custody owns physical execution and technical receipt truth; Platform removal cannot claim that every runtime resource is already erased. [A1–A4]

**Proposed evidence for the relevant owner scope.** Exhaust ordinary request, transcript, disk-journal and event queues while issuing Stop; block the main DB pool; pause the database during stop; keep an escaped descendant alive; lose the stop receipt; then restart. Assert effect rejection, honest unknown/pending status, reserved control operation and no premature successor grant. Reserve control capacity with explicit count/bytes/CPU/connection budgets rather than just a high-priority enum.

### 6. Paperclip already bounds viewer delivery; remaining fleet work is aggregate resource qualification and authorization cost

**Implemented strength.** Live delivery caps retained traffic at 1,000 items and 1 MiB per socket, including socket buffered bytes; negotiated run interests avoid full transcripts for uninterested runs; activity signals are throttled; overflow requires explicit resynchronization; persistent congestion has a five-second deadline. Delivery authorizes each visible item before sending. Permission-read failure leads to resync for the negotiated path. These are concrete defenses against slow viewers and disclosure after policy changes. [P15]

**Counterevidence against simplistic criticism.** The committed cost test sends 1,024 output events under zero-interest, one-viewer, three-browser and congested-viewer scenarios, checks queue bounds and delivery behavior, and explicitly labels SQL/network as unmeasured. It is incorrect to call this an unbounded live-event queue. [P16]

**Remaining inference.** Per-connection bounds aggregate across connected users; event authorization and serialization work scale with interested viewers and active output. Process-local EventEmitter fanout is synchronous at emission, while per-viewer delivery is asynchronous. This means viewer count, subscription cardinality and event rate belong in the fleet workload specification. It does not prove a specific user/agent limit. The correct resource equation includes connections × retained-byte ceiling plus producer buffers, state/checkpoint bytes, actual event rate and authorization work; it should not assume every connection simultaneously hits its maximum.

**Decision for Agent Teams.** AR supplies bounded canonical receipts/latest summaries under its existing contracts. Orchestrator/Platform own authorized views, snapshot/replay, interests, resync and per-viewer policies. Use a coalesced latest-state path for boards and an explicitly selected detailed transcript path. Do not move product authorization into the runner or share a cross-tenant raw-event broadcast. Bound active viewers globally/per tenant in the SaaS adapter; preserve a small local profile.

**Proposed evidence for the relevant owner scope.** Hold active execution constant and vary viewer count, viewed-run cardinality, slow links and permission churn. Check stop/lease progress and DB budget while the board consumes traffic. Measure SQL authorization calls, response sizes, CPU/heap and backlog recovery. This distinguishes the cost of running agents from the cost of watching them.

### 7. First-write-wins tenant infrastructure is a declared operational limitation; policy convergence needs an owner

**Implemented fact.** The Kubernetes tenant orchestrator documents its V1 first-write-wins behavior: it creates namespace/RBAC/quota/network resources on 404 and leaves existing resources untouched. Configuration changes do not update existing in-cluster resources. The quota function reads an existing quota and immediately returns. The unit tests cover initial resource order, the selected egress resource, annotations, namespace idempotency and concurrent-create 409 handling. [P7]

**Risk and limits.** This does not show that current tenants lack isolation. It shows that “configuration saved” and “effective policy changed” are separate states. A later quota increase, security reduction or egress-mode migration needs an explicit operational procedure. Destructive namespace recreation is a poor default for a managed product carrying active work. This report does not rely on the source comment's broad claim about the interaction of two different network-policy mechanisms; effective network behavior needs provider-specific qualification.

**Decision for Agent Teams.** Platform's intended deployment-plan/installation ownership is the right location for desired/accepted/observed revisions. Choose either immutable execution profiles plus deliberate replacement, or a bounded reconciliation contract for specifically supported mutable fields. Do not invent a universal infrastructure controller. An authorization reduction must close future admission according to its owner even while infrastructure converges; never claim success based only on a database config write. AR enforces its accepted technical capability profile, and Orchestrator must not become the owner of Kubernetes resources. [A4]

**Proposed evidence for the relevant owner scope.** Change quota/network configuration while work runs; race two reconcilers; lose the acknowledgement; restart with a stale desired revision; block the provider API; switch supported profiles. Verify observed-state reporting, no stale writer expansion, and a user-visible degraded/reconciliation state. Fully local deployment has its own policy mechanism and should not inherit Kubernetes ceremony.

### 8. Useful modules coexist with very large coordinators; use ownership evidence, not file length, to choose extraction

**Observed structure.** At the pinned snapshot, `heartbeat.ts` is 4,389 physical lines, `heartbeat/queue.ts` 5,135, and `plugin-worker-manager.ts` 4,158. Those are file-size measurements including imports/comments; they are not handwritten production LOC totals or evidence of poor architecture by themselves. The queue contains admission, dependency/priority ordering, claims, execution promotion and post-commit effects; heartbeat coordinates many policy/provider/resource phases. This makes change-impact review an important risk at those seams. [P5, P17]

**Counterevidence.** Paperclip explicitly defines domain/application/adapters, pure domain functions, constructor ports, restricted imports, module public entrypoints, and an enforced module-boundary checker. Its heartbeat rule calls for stable/smaller coordination, narrow dependencies, explicit ownership and retaining coupled decisions where extraction would obscure correctness. It warns that moving a block does not remove coupling. There are extracted run-dispatch, wake-queue and admission modules. The architecture is evolving, not uniformly an unstructured monolith. [P17]

**Decision for Agent Teams.** Use the existing Get Modular composition and owner boundaries. A mechanism with an actual shared consumer belongs in one library; a feature-local policy belongs with that feature. Avoid per-function interfaces, universal repository abstractions and class hierarchies that merely rename service closures. Keep durable grant/claim/receipt transitions together when a split would lose atomicity. Separate them from presentation, provider parsing and policy interpretation where the invariant permits it.

**Proposed evidence for the relevant owner scope.** For each new cross-owner dependency, state the invariant, writer, transaction and replacement seam; test the consumer's observable behavior. Demonstrate one provider removal/substitution without changing product policy, and one storage adapter substitution without altering domain decisions. Dependency rules plus behavior are useful evidence; file-count growth or an arbitrary class-per-entity rule is not.

## Existing scale evidence: what it does and does not establish

Paperclip retains both a failed/invalid comparison and a subsequently qualified component campaign. The earlier load artifact says host contention and unequal completed work invalidated its ABBA comparison. The later October 30 evidence says isolated steady, aligned-burst and matched two-logical-server correctness/absolute/relative gates passed. It used 300 controller fixtures, production checkpoint persistence and natural remote lease timers, 10,000 historical tasks, and defined host/process/PostgreSQL resource limits. The file explicitly says it is database/control-plane component stress, not full HTTP, harness or hosted capacity qualification. [P18]

This evidence should raise confidence in the relevant checkpoint/lease design. It should neither be discarded because it is not a full fleet test nor extrapolated to 300 or 10,000 real model processes. “Active agents” must be specified as simultaneously executing workloads with defined provider/process/resource behavior. Historical tasks and controller fixtures are different cardinalities.
