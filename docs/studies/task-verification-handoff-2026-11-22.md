## Agent start here

**Objective in one sentence:** determine whether a particular immutable deliverable meets its owner-authored requirements, identify missing or unverified behavior even when ordinary review and tests pass, and give the owner/implementing agent the next justified action. The three useful actions are correct a confirmed violation, obtain specific missing evidence or accept a supported result; an ambiguous obligation goes to its owner. Do not optimize merely for more review comments, green checks, a schema-valid answer or agreement with an oracle.

## Complex-task qualification proposal

**Reason to revise the next milestone:** D3 was valuable but involved one small 13-file family, related variants, no valid fully complete control, one selective-uncertainty development recheck and no successful live ordinary OCR comparator. It cannot qualify context discovery, ambiguity handling, cost or evidence coverage on complex customer work. The owner now wants realistic reusable E2E cases before scaling the mechanism. This is a proposal for Hassan's critique and one agreed execution card, not a new mandate to build a large benchmark platform. Retain the D3 result and the prospective team-task milestone; do not reopen D3 to obtain a clean score. The [previous single-task/adaptive proposal](https://github.com/agent-teams-ai/engineering-research/blob/abbae11c799611a28c5f53f5b4cb42cab2e8b2e9/docs/studies/task-verification-handoff-2026-11-22.md#adaptive-context-acquisition-fast-path-and-bounded-investigation-proposal-2026-11-26) remains pinned as historical rationale.

### Preferred architecture and decision sequence

One Task Verification policy/result contract, independent of OCR and ReviewRouter, with interchangeable acquisition at an actual application boundary. Fast means one structured Gateway call on a sufficient compact packet. For a simple additional-source need, batch permitted file/range/search requests, execute them through existing immutable readers, and make one follow-up assessment of the affected obligations; this is a fixed two-pass sequence, not an agent runtime. Source requests must be structured and bounded, and the follow-up receives actual retrieved observations rather than a fabricated summary. For already complex tasks, do not require a preliminary fast call solely to route them.

For genuinely multi-hop discovery, prefer a dedicated **Requirements task/profile in our existing maintained OCR repository**, with its existing reader, observation store and `llmloop`. Keep ordinary OCR/FindingDiscovery separate. Do not start another long-lived fork or duplicate the engine in TypeScript. A native profile needs a typed submission, independent task admission/receipt and bounded transport; merely adding `--analysis` or a new prompt does not satisfy managed-mode contracts. Keep the portable semantic contract in Task Verification; engine-specific code adapts observations/claims rather than becoming another completion authority. No new dynamic plugin framework or separate service. Start with a thin disposable fixed two-pass comparator on the representative fixtures; implement the native deep profile only if a measured multi-hop context gap or waste remains, or Hassan shows a smaller demonstrably safe reuse seam. Do not force a third architecture or run both paths on every case.

Route using the decisive evidence needed by each authored obligation, not model confidence alone or raw PR size. Cross-component dependencies, missing entrypoint/caller wiring, authorization, migrations, external behavior and excluded/truncated evidence are reasons to examine relevant context even if a model is confident. A complete source-supported claim can stop; a missing runtime receipt or ambiguous requirement goes to the proper owner, not to unlimited source search. Search results establish observed matches, not global absence. Use the same authorized model/profile when comparing acquisition strategies; changes to model, schema or context are explicit versions, not hidden improvements.

### Bounded partial results and transparent coverage

The current [OCR loop](https://github.com/agent-teams-ai/open-code-review/blob/8a70944f567beba9ffc12d1153e33ef5fd60967d/internal/llmloop/loop.go#L501-L522) has a grace submission round and [final-round instructions](https://github.com/agent-teams-ai/open-code-review/blob/8a70944f567beba9ffc12d1153e33ef5fd60967d/internal/config/template/prompts/behavior_final_round.md), but its current budget check is after usage and final submission may overshoot; a cancelled context skips grace and the first accepted Markdown report freezes. It does not yet guarantee typed partial findings. For a deep prototype reserve the final bounded submission before dispatch, use a soft investigation stop before the hard deadline/budget, and persist each accepted criterion/group record with its evidence before continuing. Reuse existing receipts and result contract where possible; do not create a new durable orchestration system. If final inference is refused, cancelled, malformed or unavailable, render the last persisted valid partial records mechanically, retain failed/missing observations and unresolved IDs, and never invent a conclusion. If no records exist, return unavailable/failed, not artificial partial success. A budget stop can produce a useful partial report without implying a completed review. Actual failures remain distinguishable from expected budget exhaustion.

Initial **illustrative caps for the execution-card discussion**, not measured optimal settings: fast 1 request, at most 1 targeted follow-up; deep try 4–6 total forwarded model requests for the entire assessment, including final submission, any earlier fast call, compression and paid retries (no automatic retries preferred). Reserve one final call within the cap; an escalation shares the remaining allowance rather than starting a fresh quota. More demanding groups may need a different preapproved envelope or remain partial. Bound source operations, returned bytes, per-request/context tokens, aggregate tokens/spend, concurrency and wall time separately; count actual HTTP forwards, not agent rounds or tool calls. Measure serialized bodies and provider-specific token bounds before dispatch. Batch local reads/searches, share observations by exact version/blob/range and group related requirements rather than calling the model per file/criterion. No universal 300-round default. Do not promise that a fixed count suffices for every repository.

Separate the following in the advisory result:

| Dimension | Required meaning |
| --- | --- |
| Requirement inventory | Exact owner-confirmed required IDs and optional/ambiguous text; all IDs present or explicitly missing. |
| Assessment and evidence coverage | Counts of actually assessed, supported/contradicted, inconclusive, not assessed; unresolved mandatory clauses and actual receipt scope. Mechanical ID coverage is not semantic proof. |
| Source coverage | Observed source ranges and unique files with exact revision, changed-file inventory denominator where useful, exclusions, unavailable/truncated reads/searches, and uninspected scopes. Reading part of a file is not reading the whole file; no implied exhaustive relevant-code or repository percentage. |
| Conclusion and support | Satisfied / violated / inconclusive for adjudicable requirements, precise supporting observations, missing basis, tentative leaning if useful. Separate owner clarification and optional review suggestions from mandatory fixes. |
| Execution and limits | Completed / partial / failed / cancelled etc., reason, requests, tokens/bytes, elapsed time and usage; never convert a partial stop to pass. |

Prefer understandable evidence-based support levels (strong/limited/insufficient) rather than a fake precise probability. If a confidence percentage is useful in the UX, label it explicitly as an **uncalibrated model estimate** per claim, optional/unknown when absent, with reasons; never a completion threshold or substitute for evidence. Measure actual accuracy/calibration only on separately adjudicated held-out results of sufficient size. E.g. 19 of 20 criteria assessed, 16 supported/contradicted, 3 inconclusive, 1 not assessed; 31 of 88 changed files observed (whole/partial separately). The 80% decisive coverage is an inventory statistic, not an 80% probability of correctness or of code coverage. M2 already distinguishes execution and ID inventory in its [experimental result contract](https://github.com/agent-teams-ai/task-verification/blob/996cdcb002f898a5b73ce8f9ce7931e6299b14e4/src/result-contract.ts); do not claim it already implements semantic coverage or checkpointed native submissions.

### Incomplete and ambiguous task descriptions

Accept ordinary authored prose and clear criteria without demanding a new form for every task. Preserve original text and source/revision. A small interpretation step may identify explicit obligations, optional suggestions, inferred candidates and materially ambiguous terms. Do not silently promote inferred obligations to acceptance requirements, rewrite the owner's task, or change the frozen criterion count after seeing results. When alternative reasonable meanings materially change a verdict, show the assumption and conditional outcomes or request a specific owner clarification; continue evaluating unaffected obligations. If no usable requirement basis exists, say so and keep ordinary code review independent. The model must not confidently invent an acceptance checklist, punish missing optional work, or force another implementation loop to resolve an ambiguous requirement. For a product later, version an approved clarification as a new criteria identity.

### Realistic fixtures, E2E and evaluation

Start with **two contrasting new, reusable task families** plus the already available D3/CSV evidence as small regression material. This is a proposed initial scope to discuss, not a fixed benchmark size. Prefer minimized but realistically connected runnable project snapshots or permissibly derived isolated fixtures using normal team task/PR shapes. Do not pad files or use real secrets/customer data. Example families:

- Cross-component budget/access policy: UI/API entrypoint, persisted policy, admission/authorization, async recovery/stop, stale or unavailable usage, real tests (a representative Agent Teams-style workflow).
- Plugin install/update or multi-project lifecycle: ownership and compatibility, manifest/adapter selection, persistence, retry/recovery and actual CLI/service behavior, with a realistic larger unrelated codebase and many related acceptance obligations.

Choose one medium and one materially larger/cross-module case (e.g. 8–15 and 15–25 meaningful obligations, not quotas; 50–100 changed files only if natural). Complexity is the behavior/dependency graph, not LOC. Use roughly 2–4 candidate variants per family, sharing a frozen base/requirements when appropriate: a genuinely complete control independently qualified by behavior and contract, a plausible omission or disconnected wiring (ordinary tests may stay green), a subtle cross-module or edge-case contradiction, and a legitimate unknown/ambiguous-input variant if useful. Reuse variants/checks rather than manufacture a full Cartesian matrix. Freeze expectations, exact candidate identity and model-visible information before inference. Keep oracle, known defects and expected responses outside reviewer input; distinguish legitimate uncertainty from broken setup. Hold at least one materially different candidate/requirement combination out of tuning. A repaired/tuned example remains development evidence; an independent behavioral probe checks an obligation, it is not proof of all other behavior. No third-party researcher is required merely to review the plan.

Test two distinct layers:
- **Model-free executable E2E:** materialize actual fixture Git revisions, run ordinary project checks and targeted independent behavioral probes, run the actual acquisition/assessment path through its real schema/parser/adapter with deterministic provider replies, verify references, stale/missing/duplicate/contradictory results, scope boundaries, cap/timeout/malformed final output, and retention of partial results. Native deep mode, if built, gets the same contract/admission tests and a meaningful real loop replay; ordinary OCR must not regress. Fake provider replies qualify engineering, not semantic model judgment. Use targeted invariant/property tests only if useful; reuse existing tooling, no new test platform.
- **Bounded live semantic evaluation:** after offline readiness, use a small predeclared subset of the same frozen cases with ordinary OCR/checks as the baseline and the fixed fast/two-pass policy. At least one complete, omitted/disconnected and genuine insufficient/ambiguous case across the families. Compare deep on a hard case only if it resolves a consequential context gap or its added work/quality remains uncertain. Budget each actual comparator and candidate/recheck; incomplete OCR is not zero findings. Use the same model where compatible and label differences in ordinary context. The prospective real task then checks natural inputs and the actual reader decision, not just fixture results.

Report by obligation and root cause: discovered/omitted violations, false required corrections, unsupported positive claims, useful evidence requests, ambiguity handling, partial-result integrity, duplicate findings vs ordinary OCR, model requests/latency/spend and recurrent preparation/reader work. Record case size, input scope and actual coverage. Require no material unsupported success or falsely reported complete run in the qualified cases, correct identity and limit handling, and actionable evidence-backed differences before recommending broader use. A finite fixture suite improves confidence in these cases; it cannot guarantee universal correctness. If fast/two-pass is adequate, defer the native mode; if deep materially improves a hard case within acceptable cost, qualify that narrow mode; if neither is useful, retain ordinary review/evidence or state the specific obstacle. Avoid repeated testing to obtain a preferred verdict.

## Adaptive context acquisition: fast path and bounded investigation (proposal, 2026-11-26)

**Recommendation for the next design decision:** reuse one semantic requirements-assessment mechanism with adaptive context acquisition. A small, reproducible packet and one structured call are the cheap path; a bounded follow-up may obtain decisive missing source. Go directly to investigation when a compact packet cannot support the task. Do not make model-reported confidence or `inconclusive` the sole escalation trigger. A confident positive after reading only a helper can miss missing caller wiring; a confident negative from an incomplete diff can falsely accuse already implemented behavior. This is a design hypothesis for the bounded qualification proposal and prospective pilot, not authority for new paid execution, a product feature, or automatic approval.

### Structured output: distinguish shape, truth and action

The important weakness is not malformed JSON. D3 already returns well-formed structured results. The [frozen experimental schema and decoder](https://github.com/agent-teams-ai/task-verification/blob/9367ce4e7dee40d076f654397fd535a09e2d6c3a/synthetic/next-family/lib/task.mjs) provide one status, references, explanation and a single correction string for each criterion. That string conflates a required code change, a request for evidence, clarification and optional advice. A composite criterion can contain both a demonstrated violation and an unresolved obligation. Do not convert that into an apparently complete correction request.

Proposed product direction (not an adopted API): preserve authored criterion identities/text. When a criterion has several mandatory obligations, retain independently scoped claims, their evidence references and their remaining unknowns. If clause identities are required, derive them from a reviewed/frozen interpretation of the authored requirement, not an unconstrained model-invented checklist. For a conjunctive requirement, a small deterministic reducer over admitted, applicable judgments can return violated for a demonstrated required contradiction; satisfied only if all required obligations are supported; otherwise inconclusive. Missing/invalid execution and stale evidence remain separate from a semantic inconclusive finding. Alternative/disjunctive or ambiguous requirements need their explicit semantics, not this conjunctive rule. A typed claim is not an admitted fact merely because it is valid JSON or has a real source reference.

For later consumers, keep the following output categories distinct:

| Category | Reader/agent action |
| --- | --- |
| Supported mandatory violation | Correct the named behavior, with a concrete counterexample or sufficient source basis. |
| Missing evidence | Obtain the named applicable observation or source; not automatically rewrite code. |
| Ambiguous authored obligation | Request an owner decision; do not silently weaken or expand it. |
| Optional code-review observation | Retain as advisory, not a completion gate. |

Keep raw claims and contradictory evidence; resolve references against the frozen inventory and candidate, and do not suppress an ordinary OCR finding because of a criteria status. Deduplicating exact identities is deterministic; grouping different statements as one underlying defect requires justified equivalence, not a text-similarity threshold alone. No model may grant execution authority or commit Work. Reuse the [M2 result contract](https://github.com/agent-teams-ai/task-verification/blob/9367ce4e7dee40d076f654397fd535a09e2d6c3a/src/result-contract.ts) and applicability/admission boundaries. D3 retained the original wire schema; the prospective pilot should first render these distinctions in a small report using existing contracts. Do not represent human-adjudicated output as autonomous model quality or automatically route disputed corrections.

## Product objective and boundaries

The original vision is to assess an immutable deliverable against explicitly supplied, versioned acceptance criteria, identify missing or unverifiable outcomes, and provide actionable feedback. ReviewRouter is the first consumer; Orchestrator is a later consumer. The portable capability returns facts and advisory assessments. Work Coordination retains terminal Work authority.

Iliya is the report reader and decision owner. Hassan prepares and runs separately scoped bounded research. A third independent expert is not required. Independent expected behavior means that reviewer output does not define its own correct answer.

Retain these boundaries:

- Criteria come from the task owner. The model may explain a criterion but cannot silently add obligations, drop a clause or weaken the requested outcome.

- Ordinary OCR findings remain available. A criteria result neither overrides them nor automatically confirms them.

- Results apply to the exact candidate, criteria and assessment profile. Publication, permissions, credentials and final product decisions remain with their existing owners.

- The reviewer reads the candidate. Existing authorized runners produce execution evidence when needed.

- Specification generation, automatic implementation, unrestricted test generation, merge gating, Work completion, a new service/database/queue and a stable cross-product SDK are outside this research.
