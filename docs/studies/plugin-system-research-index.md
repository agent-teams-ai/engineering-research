### Transferable strengths and bounded counterexamples

| System / source class | Useful existing mechanism | Risk or explicit limit for our scenario |
| --- | --- | --- |
| Piral; **executed browser cases P1/P2/B1-B3** | Actual UI registrations, asynchronous setup and cooperative resource bridging; its reference-specific extension disposer preserved a successor | A delayed page disposer addressed by route removed the successor. Teardown is documented as synchronous, so absence of arbitrary async teardown is **not** a broken Piral promise. Outer completion did not prove useful readiness |
| Get Modular Resources; **public package and bridge probe** | Scoped acquisition, joined cleanup flights, debt, retry and ownership-aware release; reuse rather than building another cleanup stack | A cleanup scope does not choose or atomically admit the implementation used by each async call. The separate lifecycle kernel is still a private/unreleased candidate |
| Effect; **executed Node case E1** | Existing native lifetime/Layer tools keep their own scope and error semantics | A second close returned before the original finalizer released a listener. Keep the first close outcome when proving cleanup; this is a bounded observation, not a claim that Effect always leaks |
| Native Federation / Module Federation; **inspected implementation evidence** | Native Federation contains staging/rollback protections worth retaining; remote loading and sharing can reduce reinvention | Imported module identity, singleton sharing, stale clients, state migration and already-running work require separately qualified contracts. No full-app outcome was executed here |
| OpenComponents; **inspected implementation evidence** | Existing reconnect-related behavior is useful evidence for UI contributions | A reconnect mechanism does not prove atomic multi-cohort replacement or complete state continuity across arbitrary consumers |
| OSGi; **inspected implementation evidence** | Binding a successor before unbinding the predecessor is an instructive ordering pattern | This is not evidence of transactionally atomic replacement across all state and external effects |
| Extism / Wasm; **conditional technology research** | Separate execution and host/guest contracts can be useful when a consumer really needs them | Backend-specific capabilities, cleanup and trust must be qualified; do not require Wasm or a process boundary for ordinary cooperative TypeScript |

The [full source register and independent reviews](https://github.com/agent-teams-ai/extension-foundation/blob/10deea1a11748df1fcbfc2766033c462fce3acd0/docs/research/live-module-update-design-validation-2026-11-23.md)

### Failure patterns to design against

| Failure shape | Required boundary / future falsifier |
| --- | --- |
| Old disposer deletes a replacement by stable name/route | Scope teardown to the exact registration instance; execute a late-disposer successor-survival test |
| Setup promise fulfilled while useful contributions are gone | Keep separate prepared, published and **usefully adopted** observations; verify a real consumer operation |
| Timeout, lost acknowledgement or caller cancellation classified as rollback | Preserve the original attempt and reconcile the authoritative decision before replay or cleanup |
| Reader count reaches zero so artifacts are deleted | Separately account for in-flight cleanup, old-client, history and artifact holds |
| Cleanup retry considered complete merely because an idempotent call returned | Join the actual original cleanup flight; retain debt and failure receipts independently of successor use |
| New candidate evaluated before ownership/trust is established | Qualify loader-side custody and reject unsupported effects; no generic in-process isolation promise |
| Application reconstructs the entire update state machine around callbacks | The proposed reusable library owns planning, preparation, reconciliation, adoption and retirement; products supply narrow authority/state primitives |
| Private Get Modular kernel copied into the new package or every product | Qualify a supported upstream mechanism through its owning package before an adapter promises atomic admission/retention |
| One universal plugin interface, database, state migrator or workflow engine required everywhere | Select a capability-specific profile and one cohesive update-operation feature; no mandatory Effect, PostgreSQL, Temporal or Wasm |
